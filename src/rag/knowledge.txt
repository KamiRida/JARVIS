# 35. JARVIS — CURRENT RAG SYSTEM

**Stability: Current as of September 2026**

Kamran is currently learning to build RAG from scratch rather than merely importing a complete abstraction.

The current project includes:

`src/rag`

and a file such as:

`knowledge.txt`

A `read_context()` function reads the knowledge.

An early bug caused `return` to be inside the loop, meaning only the first line was returned.

After fixing this, the knowledge contained multiple chunks/lines.

At one point the document embedding shape became approximately:

`(10, 2048)`

while the query embedding shape was:

`(2048,)`

This confirmed that separate knowledge items were receiving separate embeddings.

The embedding model currently used is:

**Qwen/Qwen3-VL-Embedding-2B**

via `SentenceTransformer`.

Dependencies such as Pillow and torchvision were installed while resolving model/image-processor issues.

Kamran understands that an embedding converts text into a high-dimensional numeric vector representing semantic information.

He understands the basic intuition of cosine similarity:

* same direction → similarity near 1
* 90-degree difference → similarity near 0
* opposite direction → similarity near -1

He understands that cosine similarity uses:

`dot product / (norm(query) × norm(document))`

and that normalization removes vector-magnitude effects so the comparison primarily reflects direction.

Kamran recently implemented cosine similarity manually with NumPy rather than relying entirely on a helper function.

He debugged a mistake where `np.abs()` was used instead of the vector norm.

He also debugged an indexing problem where the retrieval system always returned the final chunk because the loop asked whether the maximum existed anywhere in the similarity list rather than whether the current index contained the maximum.

The retriever now successfully selects a relevant chunk.

Current basic RAG pipeline:

1. Read context.
2. Convert context chunks to embeddings.
3. Convert user question to embedding.
4. Calculate cosine similarity between query and each chunk.
5. Identify highest similarity.
6. Retrieve the corresponding original text.
7. Next stage: place retrieved context into the LLM prompt alongside the user's question.

At present, knowledge is effectively close to **one line = one chunk**.

The planned improvement is semantic chunking.

# 36. JARVIS — FUTURE RAG / MEMORY DESIGN

**Stability: Planned**

Kamran wants JARVIS to know extensive information about him without passing pages of context into every prompt.

The long-term system should maintain a large personal knowledge base.

The intended process is:

personal knowledge
→ semantic chunks
→ embeddings
→ retrieval
→ relevant top chunks
→ LLM context

Rather than storing thousands of unrelated individual sentences, source documents should be organized by topic.

* career

* projects
* family
* preferences
* current goals

Each coherent topic can become one or more chunks.

The retrieval layer can still use a Python list or similar indexed structure internally.

* Chroma vector database

* importance scoring
* deduplication
* contradiction handling

The recommended learning sequence Kamran has been following intentionally starts with **Ollama + NumPy cosine similarity** before introducing vector databases and rerankers. # 74. CHUNKING GUIDANCE FOR THIS DOCUMENT

**Stability: Technical instruction**

Do NOT embed this entire document as a single vector.

Use section headings as natural semantic boundaries.

A reasonable initial strategy is:

* each numbered section = candidate chunk,
* merge very small adjacent sections when strongly related,
* split extremely large sections when they cover multiple independent concepts.

The retriever should maintain an association between each chunk's embedding and the original text.

Later each chunk can also carry metadata such as:

* topic
* entity
* date
* stability
* importance
* source
* last updated

Example:

`topic: education`
`subtopic: uchicago-transfer`
`stability: current`
`updated: 2026-09`

This makes later temporal reasoning and memory maintenance easier.
